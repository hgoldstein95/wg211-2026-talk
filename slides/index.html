But then I kind of pulled back the curtain a little bit on what Claude had done. And I think this kind of model, even in the most sort of anti-testing view of the far-flung future, is where I think testing continues to be super relevant. No matter how much we try, I think proofs will be more and more common within software components, but then when trying to match up components between languages, tests are going to help us keep all of that in check.

What we can observe is that if your predicate looks like fold of something, we should be able to say, well, what if we found a compatible unfold? If we found a compatible unfold, then if fold takes some value to true, then the unfold should take true to a nondeterministic set of values that satisfy the fold. 

theorem fold_unfold_inverse
    (alg  : ListF α β → β)
    (step : β → G (ListF α β)) :
    (∀ b, (step b).support =
      fun l => alg l = b) →
    (∀ b, (List.unfold step b).support =
      fun xs => List.fold alg xs = b)
Formally, this looks like this. This is a theorem that says if we have a step generator whose support satisfies the algebra of the fold, then we can have an unfolding that step gives us a thing that satisfies the full fold.

What should a
generator denote?

Okay, now, let’s look at how are we going to represent generators as distributions?

One answer to this question comes from QuickChick. And in QuickChick, a generator is a mapping from seeds to values, and it defines support as just all the values for which there exists some seed that produces the value. So in this case, the support of our genFrames function would be framesOK, which is all well and good. 

def genMostlyEmpty : G (List Frame) :=
  frequency [
    (999999, pure []),
    (1, genFrames)
  ]
            

genFrames.support      = framesOK
genMostlyEmpty.support = framesOK
But when you have really weird generators with weird distributions, like this one, which almost all of the time produces an empty list, and then with, like, weight one produces an actual reasonable list of frames. Both of these have the same support. And so this is clearly not what we want, in terms of being able to prove the things that we need to guarantee our generators do what we want. 

def SPMF (α : Type) : Type :=
  {μ : α → ℝ≥0∞ // (∑' a, μ a) ≤ 1}
So instead, rather than thinking of our generators as denoted by set, we’re going to think of our generators as denoted by probability distributions. And concretely, we’re going to use this type SPMF, where μ is a mass function. It’s a mapping from values to real numbers. And then, we have this stipulation that the total mass has to be at most one. This is what we need in order to be a kind of reasonable probability distribution. Now, you might wonder why at most one. Well, that’s because I want to be able to allow these generators to potentially diverge. So what we can think is that when the total mass sums to less than one, the rest of the mass goes to divergence. 

def loop : G Bool := loop

def genCoin : G Bool :=
  oneOf! [
    fun _ => pure true,
    fun _ => pure false,
    fun _ => loop
  ]
So for example, here’s this very silly generator loop. And what loop does is it loops forever. And then we have genCoin. But genCoin, with some weight produces true, with equal weight produces false, and then with equal weight loops. And what we can see is that the distribution of this ends up looking like as follows. One third probability goes to true, one third goes to false, and then one third is this divergence probability, which we can track in proofs using our subprobability mass functions.

Like genFrames here doesn’t actually terminate structurally because it makes a recursive call on nothing at all. However, we can still, with the help of subprobability mass functions, show that because the mass in the limit sums to one, there’s no probability of divergence.

What can we do with this representation? Well, we can prove the same things that we used to be able to prove. We can prove that our generator is sound and complete with respect to a particular predicate. So, in particular, that its support is exactly framesOK. But now we can prove new things too. We can prove almost sure termination, for example, which says that genFrames actually does put zero mass on divergence, and we can also prove things about expected length. So, for example, we can show here that genFrames, because it is not very well distributed, produces an expected length of a list that’s actually less than one. This is pretty bad. Okay, and I have one more neat trick to sort of drive home all of the, like, fundamental programming that I’ve been doing on this system. So I have this macro that does frequency. So I’ve been showing this off previously in the talk, but there’s this problem that can happen with generators where, if you have a frequency function, which is gonna take a list of subgenerators, if you’re not careful, every time you, like, go through a recursive loop, it will reallocate that list of subgenerators. And this can, like, really blow up your runtime because you’re just allocating way more memory than you actually should be. And so, inspired by a paper by some of my co-authors and myself that appeared at OOPSLA just last week, what I do is I have, instead of having frequency be a function, frequency is a macro. And that macro expands to this structure. Basically, it carries two different things: a proof interpretation, which is the real list; a runtime interpretation, which is the kind of if-else chain that that list would expand out to; and then a bridge proof, which guarantees that the two are in sync. This allows us to run things much faster at compile time, because the proofs get erased. But it still means that when we’re writing our proofs, we get nice behavior.
And this turns out to be extremely effective. So when using the macro version on a bunch of different benchmarks, the Basalt library is substantially faster than the unoptimized version. It’s also substantially faster than Haskell QuickCheck. So it turns out that, actually, this is faster than both Haskell QuickCheck and OCaml QuickCheck with a couple of lightweight optimizations.
