What’s the point
of testing
anymore?

But I want to start this talk with a question that I’ve been asking myself lately that I think is a kind of uncomfortable one, but that has to be asked, which is, what’s the point of testing anymore?

Lean Port of Minecraft

To see why I’d even ask that question, here is an implementation of Minecraft written fully in Lean. And you can see the characters placing blocks, jumping around, flying around.

And in lots of the places where I would have had tests in this code base, I instead have proofs. So I’ve been able to prove that the entities collide properly with blocks, and that clicks don’t get lost, and that faces are only drawn if they’re supposed to be visible.

This took me Claude

2.5 hours

And this wasn’t some like monumental undertaking. This took me about two and a half hours. It took Claude two and a half hours. And my initial reaction to this was, maybe I should stop researching testing, because maybe in the future, in the far-flung future, actually all we’re going to be doing is proving pieces of software correct.
But then I kind of pulled back the curtain a little bit on what Claude had done. And what I found was that while the core game logic of this game was, indeed, written in Lean, the rendering logic and a bunch of the, like, calls to the graphics libraries happened with a library in C called raylib, that Lean just called into. And actually, I don’t have a problem with this. I think raylib’s quite a nice library. But there certainly weren’t all of the proofs that I could possibly have wanted. And so I asked myself, you know, how can we make this picture more robust? And what I did, what I decided to do, was to build a model. So now we have a model of how raylib should behave, written in Lean. And then we test that that model actually agrees with how raylib renders things. Once we have that, we can prove the association between the model and the game logic, and then we can have really end-to-end proofs about the game’s execution without having to prove things about the C directly.
And I think this kind of model, even in the most sort of anti-testing view of the far-flung future, is where I think testing continues to be super relevant. No matter how much we try, I think proofs will be more and more common within software components, but then when trying to match up components between languages, tests are going to help us keep all of that in check.
So let’s pull back the curtain a little bit and look at that testing a little bit deeper. So, we have our model in Lean, and we have our C code in raylib. And what we’re going to do is we’re going to randomly generate sequences of commands. We’re going to run them on each of these, and we’re going to make sure that after we run those commands, the same things have happened, both in the model and in raylib. That’s very nice, but where do we get these sequences of commands? The answer is generators. Generators are the property-based testing term for these programs that produce random data that we can use for testing.

How do we build great generators?

And that’s going to be the topic of the rest of this talk. Specifically, I’m going to ask, how do we make generators good? And also kind of a subquestion is like, what should good even mean?
I’m going to present two different papers. One is called Palamedes. This was presented at PLDI this past year. And the other is called Basalt, which is my kind of take on a new foundation for property-based testing generators, and hopefully that’s coming soon to a conference near you.

Palamedes

Synthesizing Generators

So let’s start with Palamedes. Palamedes, at its core, allows you to automatically synthesize PBT generators. So let’s look at why you might want to do that.

So here’s a theorem about our Minecraft game, and it’s about the slots in your inventory. A slot is either empty, or it holds a stack of blocks, and a stack is somewhere between 1 and 64 blocks. That’s what slotOK says. Either the slot is none, or it’s some of n, where n is between 1 and 64. And the theorem says that if you have a slot that’s okay, and you take one block out of it, then you still have a slot that’s okay. So slotOK is our precondition. Now, if we want to test this, we need slots. A slot here is just an optional number, so we could generate a whole bunch of optional numbers. But most of those are not okay slots, right? A stack of zero blocks is not a stack, and neither is a stack of 90,000. Only a handful of these satisfy the precondition, so almost all of our tests would check nothing at all. What we’d like is a generator that produces all sorts of okay slots, but also no invalid slots. 

∃ g : G α, ∀ a, a ∈ g.support ↔ P a
So what is it that we want, precisely? Well, the thing we want, really, is a solution to this theorem. So we want to know that there exists some generator g, such that for every value a, a is in the support of that generator, the values that it can produce, if and only if P holds of a. And P in our case is slotOK. So you want a generator that will produce exactly the values that satisfy P.

Okay, so let’s do that for slots. Here is the body of slotOK again. A slot is okay if it’s none, or if there exists some n between 1 and 64 such that the slot is some of n. Can we build a generator just from this? And I think we can. So first we have a disjunction, and that disjunction can just be a random choice. So we can just use this oneOf combinator to make a random choice between two different things. Then in the case where the slot is supposed to be none, we can just generate none. If our slot is constrained to be one value, we can generate exactly that. Now, when we have an existential, what we can do is we can sample from a subgenerator, so we can find some subgenerator that can do the part that generates n. And then we can use that n later. Then for this n between 1 and 64, we can just generate between 1 and 64. And then for this last thing where the slot has to be some of n, we can just use pure once again. What this amounts to is actually a proof. So when we put this generator back together, we can see that the thing that produced it is a sequence of tactics. And this is actually literal. So in Lean, this is literally a sequence of tactics. We apply a bunch of tactics over and over again. And we get a generator that looks like this. And because this tactic sequence is well structured and quite straightforward, we can actually use proof automation to do this. So we can use the aesop tactic in Lean, which does proof search, to automatically find this proof. 

def genSlot : G (Option Nat) := by
  generator_search slotOK
            

def genSlot : G (Option Nat) :=
  oneOf [
    pure none,

So here is what it looks like to use Palamedes. You write a definition, you give it a type, and for the body you write by. And by is how you start a proof in Lean. Then you write generator_search and the predicate. So generator_search is a tactic, and the body of this generator is a proof script. And when Lean runs that tactic, the thing it fills in is the generator that we just built by hand. If you write generator_search?, it will print that generator out for you. 

/-- Duration of one frame. -/
def Frame := Nat
            

def framesOK (fs : List Frame) : Bool :=
  List.fold
    (fun
      | .nilF => true
      | .consF n ok => n ≤ 200000 && ok)
    fs
Okay, so that takes care of predicates like slotOK, that aren’t recursive. But most of the things we want to generate are recursive. So here’s another one from the game. The game runs on a list of frames, and a frame, for us, is just how long it took. And framesOK says that every duration in the list is less than 200,000. It’s written one layer of the list at a time. So the empty list, nilF, is okay. And a cons, consF, is okay if its head is less than 200,000, and the rest of the list was okay. Now, let’s look at the thing that makes this more complicated, which is this fold.
What we can observe is that if your predicate looks like fold of something, we should be able to say, well, what if we found a compatible unfold? If we found a compatible unfold, then if fold takes some value to true, then the unfold should take true to a nondeterministic set of values that satisfy the fold.
And the nice thing is that we only have to find that unfold one layer at a time. If we have a generator that undoes one step of the fold, so it takes true back to the layers that the step accepts, then unfolding that generator undoes the whole fold. And that’s a theorem, so we only had to prove it once. 

theorem fold_unfold_inverse
    (alg  : ListF α β → β)
    (step : β → G (ListF α β)) :
    (∀ b, (step b).support =
      fun l => alg l = b) →
    (∀ b, (List.unfold step b).support =
      fun xs => List.fold alg xs = b)
Formally, this looks like this. This is a theorem that says if we have a step generator whose support satisfies the algebra of the fold, then we can have an unfolding that step gives us a thing that satisfies the full fold. 

def framesOK (fs : List Frame) : Bool :=
  List.fold
    (fun
      | .nilF => true
      | .consF n ok => n ≤ 200000 && ok)
    fs
              

def framesOK : List Frame → Bool
  | [] => true
  | n :: fs => n ≤ 200000 && framesOK fs
                

def genFrames :=
  List.unfold
    (fun () => oneOf [
      pure .nilF,
      do
        let n ← chooseNat 0 200000
        pure (.consF n ())
    ])
    ()
So, using this theorem, we can take our framesOK predicate and turn this into a genFrames generator that just unfolds one step. And that step has the same shape as the slot generator that we synthesized a moment ago. Either stop, or pick a number in range and keep going. The same rules find it. And it turns out, actually, we don’t need to write it as a fold at all. If we write just as a normal Lean function, Palamedes can figure this out too. I think the thing that I want to emphasize with this piece of the talk is that the synthesis algorithm that we’ve done is not some, like, entirely bespoke piece of software. Instead, what it’s using is a bunch of metaprogramming in Lean to achieve this goal. And it’s doing it with a whole bunch of derived equivalence principles on the underlying generators and predicates.
And this scales beyond simple things like genFrames. So we can produce generators for red-black trees, and we can also do well-typed lambda terms. 

/-- Red-black trees. -/
def isRBT (t : Tree (Color × Nat))
    (h lo hi : Nat) : Bool :=
  isRR t && isBST t (lo, hi) && isBH t h
                

def genRBT (h lo hi : Nat) :
    G (Option (Tree (Color × Nat))) := by
  generator_search
    (fun t => isRBT t h lo hi)
                

/-- Well-typed lambda terms. -/
def isWellTyped (Γ : List Ty)
    (t : Term) : Prop :=
  ∃ τ, getType t Γ = some τ
                

def genWellTyped (Γ : List Ty) :
    G Term := by
  generator_search
    (fun t => isWellTyped Γ t)
Here is what those two look like. Each one is a predicate, and then a generator that is just a call to generator_search on that predicate.

Palamedes

Synthesizes generators that are correct by construction.

Automates synthesis with Lean’s tactic metaprogramming.

Handles recursive functions by matching folds with unfolds.

The upshot here is that Palamedes lets us synthesize generators from predicates and ensure that they’re correct by construction. It uses Lean’s tactic metaprogramming to automate the synthesis process, and it handles recursive functions by matching folds with unfolds.

And so, what I set out to do was to build a foundational framework for proving things about property-based testing generators that helps us keep both automation like Palamedes and automation like Claude on the rails. So, in Basalt, you can prove distributional facts about generators, and you can run them efficiently as a generator library.

But support alone can’t tell one distribution from another. Here is genSlot again, written with frequency so that we can see its weights, next to genSlot', which is the same generator re-tuned so that nine slots in ten are full. Both of these have the same support. And so this is clearly not what we want, in terms of being able to prove the things that we need to guarantee our generators do what we want. 

def SPMF (α : Type) : Type :=
  {μ : α → ℝ≥0∞ // (∑' a, μ a) ≤ 1}
So instead, rather than thinking of our generators as denoted by set, we’re going to think of our generators as denoted by probability distributions. And concretely, we’re going to use this type SPMF, where μ is a mass function. It’s a mapping from values to real numbers. And then, we have this stipulation that the total mass has to be at most one. This is what we need in order to be a kind of reasonable probability distribution. Now, you might wonder why at most one. Well, that’s because I want to be able to allow these generators to potentially diverge. So what we can think is that when the total mass sums to less than one, the rest of the mass goes to divergence. 

def loop : G Bool := loop

def genCoin : G Bool :=
  oneOf [
    fun _ => pure true,
    fun _ => pure false,
    fun _ => loop
  ]
So for example, here’s this very silly generator loop. And what loop does is it loops forever. And then we have genCoin. But genCoin, with some weight produces true, with equal weight produces false, and then with equal weight loops. And what we can see is that the distribution of this ends up looking like as follows. One third probability goes to true, one third goes to false, and then one third is this divergence probability, which we can track in proofs using our subprobability mass functions. 

def genFrames : G (List Nat) :=
  oneOf [
    fun _ => pure [],
    fun _ => do
      let n ← genElapsed
      let ns ← genFrames
      return n :: ns
  ]
When you have a generator like genFrames, which actually does terminate. Now, it doesn’t look like it terminates, mind you, right? Like genFrames here doesn’t actually terminate structurally because it makes a recursive call on nothing at all. However, we can still, with the help of subprobability mass functions, show that because the mass in the limit sums to one, there’s no probability of divergence. 

theorem genFrames.sound_complete :
    IsSoundAndComplete genFrames framesOK

theorem genFrames.terminates :
    IsAlmostSurelyTerminating genFrames

theorem genFrames.expect_length :
    HasExpectedValue genFrames (·.length) ≤ 1
What can we do with this representation? Well, we can prove the same things that we used to be able to prove. We can prove that our generator is sound and complete with respect to a particular predicate. So, in particular, that its support is exactly framesOK. But now we can prove new things too. We can prove almost sure termination, for example, which says that genFrames actually does put zero mass on divergence, and we can also prove things about expected length. So, for example, we can show here that genFrames, because it is not very well distributed, produces an expected length of a list that’s actually less than one. This is pretty bad. And so it would tell us that we need to go back and retune the generator to make it have a better distribution.

And the first thing is we change the way generators are represented. So, like I said, in QuickChick, a generator is a function from seeds to values. Here, I wanted generators to be more flexible than that. So a generator here has a tagless final embedding of a generator type class. So the actual type of genFrames is for all G, that’s a type constructor. If G is an instance of the generator type class, then G of List Nat. This allows us to not fix a particular interpretation of generators too early.

  instRandomChoice : RandomChoice G

So, what does this Gen type class look like? We have this type class here, which has two big pieces. So the first is sort of classic QuickCheck. A generator is a monad with random choices. That’s all well and good. That’s pretty normal. The other weird thing that we do is that we require that our generators be CCPOs. These are chain complete partial orders. And the reason that this is necessary is because Lean has a fairly recently implemented infrastructure for doing non-terminating programs, provided that they are built in a CCPO. And behind the scenes, what they’re doing is applying a Knaster–Tarski fixpoint to tie the knot and give you a well-formed structure, even though you wrote a potentially non-terminating computation. 

class Gen (g : Type u → Type v) where
  instInhabited    : ∀ α, Inhabited (g α)
  instMonad        : Monad g
  instRandomChoice : RandomChoice g
  instCCPO         : ∀ α, CCPO (g α)
  instMonoBind     : MonoBind g
And this is the full definition in Basalt. It has two more pieces. Every generator type has to be inhabited, and bind has to be monotone, which is what lets partial_fixpoint go through a do block.

Run Prove

=

Richey and Cutler et al., Fail Faster, OOPSLA 2026

And so, inspired by a paper by some of my co-authors and myself that appeared at OOPSLA just last week, what I do is I have, instead of having frequency be a function, frequency! is a macro. And that macro takes the list apart while Lean is elaborating the code. So the first entry has weight 2, and it turns into a test against 2. The second has weight 5, so its test is against 2 plus 5, which is 7. The third one is tested against 10. And 10 is the total weight, so the draw is a number between 0 and 9. And what we’re left with is this if-else chain, with no list in it at all. But the macro doesn’t throw the list away. Basically, it carries two different things: a proof interpretation, which is the real list; a runtime interpretation, which is the kind of if-else chain that that list would expand out to; and then a bridge proof, which guarantees that the two are in sync. This allows us to run things much faster, because the list and the proof are gone by the time the program runs. But it still means that when we’re writing our proofs, we get nice behavior. And this is the same move as Palamedes. It’s a Lean program that writes a Lean program, and writes its proof too.
And this turns out to be extremely effective. So when using the macro version on a bunch of different benchmarks, the Basalt library is substantially faster than the unoptimized version. It’s also substantially faster than Haskell QuickCheck. So it turns out that, actually, this is faster than both Haskell QuickCheck and OCaml QuickCheck with a couple of lightweight optimizations.
