Palamedes

Synthesizing Generators

Okay. So let’s start by talking about Palamedes. At its core, Palamedes engages with a particular problem that we have with generators, which is that in PBT, our generators are often constrained.

So take this theorem that we might want to test. So this engages with a data structure called a slot. And this is from the Minecraft clone, so the player has a bunch of inventory slots, and those inventory slots can be in one of two states: either there’s nothing in the slot, so the slot is none, or there’s something in the slot and it’s a stack of items between one and 64 values. So this slotOK predicate says what it means for a slot to be well formed. And then we have this theorem, takeOne_ok, which says that if we have a slot that is well formed, then taking one out of that slot still gives us a slot that’s well formed.

Now, what we might start doing is just generating slots at random. But if we do this, we’re going to get a lot that aren’t valid. And this is just because the numbers end up falling outside the valid range. So what we’d like to do is produce a generator that can produce valid slots by construction.

And if we can prove this theorem constructively, then we can lift the witness out, and that generator will be exactly the generator we want for testing.

To give you a taste of what this looks like, I’m not going to be able to go into the kind of gory details. But if you have this predicate, our slotOK predicate, and you break it up into pieces, you can see how each of those pieces corresponds to a different piece of a corresponding generator.

So, for example, a disjunction corresponds to a random choice. An equality constraint corresponds to returning a particular value. An existential corresponds to a monadic bind, a kind of sample, and then continue. A range predicate corresponds to a random choice in a range. And when you put it all together, you get a generator which, by construction, satisfies the predicate that we started with.

Now, what’s especially special about this in Palamedes is that we didn’t have to implement a whole bunch of specialized code to implement this synthesis. Instead, what happened is that this synthesis happens via tactics in Lean. So this is just metaprogramming. Lean’s tactic system is built in Lean, so it’s Lean code that is doing all this under the hood. And this string of tactics corresponds to breaking down the predicate that we saw before, and building up the generator that we see now.

Taking this a step farther, we actually don’t have to write all of these tactics manually. We can use proof search. And so the Aesop tactic in Lean uses proof search to assemble a bunch of tactics into a proof. And in fact, we use Aesop under the hood in Palamedes to actually do the core synthesis of the generators.

Okay, so that’s the core idea behind Palamedes, but of course, I just showed you a very simple example. And one other thing that predicates often have, which can be difficult to deal with, is recursion. So now I just want to tell you quickly how we do that.

I’m going to introduce a different predicate, framesOK, which just constrains a list of frame durations for the graphics renderer. And the thing to focus on is that it’s written with a fold.

And in Palamedes, we make generators from predicates that have folds via unfolds. Basically, we observe that if a fold would take some data structure and give us true, then an unfold could take true and give us a bunch of data structures for which that fold would then have given us true. We can kind of round trip the fold and the unfold.

And this makes a lot of sense if you consider the fact that turning a predicate into a generator is a lot like finding the inverse of that predicate. You’re just finding a kind of nondeterministic inverse, because there are lots of values that the predicate might map to true.

I don’t have time, again, to get into the really gory details of this process. But at a high level, what we do is we show that if one step of the fold can be inverted by one step of the unfold, then by construction, the unfold can invert the fold. 

theorem fold_unfold_inverse
    (alg  : ListF α β → β)
    (step : β → G (ListF α β)) :
    (∀ b, (step b).support =
      fun l => alg l = b) →
    (∀ b, (List.unfold step b).support =
      fun xs => List.fold alg xs = b)
            

def framesOK (fs : List Frame) : Bool :=
  List.fold
    (fun
      | .nilF => true
      | .consF n ok => n ≤ 200000 && ok)
    fs
              

def framesOK : List Frame → Bool
  | [] => true
  | n :: fs => n ≤ 200000 && framesOK fs
                

def genFrames :=
  List.unfold
    (fun () => oneOf [
      return .nilF,
      do
        let n ← chooseNat 0 200000
        return (.consF n ())
    ])
    ()
              

def genFrames : G (List Frame) :=
  oneOf [
    return [],
    do
      let n ← chooseNat 0 200000
      let ns ← genFrames
      return n :: ns
  ]
And this is how Palamedes can do all sorts of really interesting generators. So we can do the framesOK generator. We can also do a version of the framesOK generator that isn’t written using fold, by, under the hood, observing that this recursion actually is a fold and turning it into a fold.
And we can also do fun things like red-black trees and STLC terms. Palamedes is actually quite expressive in the range of generators that it can synthesize. 

/-- Red-black trees. -/
def isRBT (t : Tree (Color × Nat))
    (h lo hi : Nat) : Bool :=
  isRR t && isBST t (lo, hi) && isBH t h
                

def genRBT (h lo hi : Nat) :
    G (Option (Tree (Color × Nat))) := by
  generator_search
    (fun t => isRBT t h lo hi)
                

/-- Well-typed lambda terms. -/
def isWellTyped (Γ : List Ty)
    (t : Term) : Prop :=
  ∃ τ, getType t Γ = some τ
                

def genWellTyped (Γ : List Ty) :
    G Term := by
  generator_search

Basalt

Foundations for Generators

Okay, next, I’m gonna talk about Basalt, which is my new foundations for how PBT generators should be expressed.

What does it mean for generators to be correct?

And the Basalt project started with this question: what does it mean for generators to be correct? You might think that it’s the thing that I said just a few slides ago, which is what Palamedes enforces, which is that the generator generates exactly the values that satisfy the predicate.

Prior work denotes generators as

sets (their support),

we want to talk about them as

distributions.

The fundamental problem here is that we have a bunch of competing concerns, right? We need soundness and we need completeness, but we also need to be able to talk about the distribution.

Basically, prior work, which includes the QuickChick paper, but also Palamedes, uses sets as their denotation of generators. And what we really need is distributions. We need to be able to prove things about generators at the level of distributions. 


def SPMF (α : Type) : Type :=
  {μ : α → ℝ≥0∞ // (∑' a, μ a) ≤ 1}

In order to do this, we need a new kind of semantic domain in which to interpret generators. And I’m going to choose subprobability mass functions, or SPMFs. And a subprobability mass function is two things. It’s a mass function: it assigns a real number mass to each value of type α. And then we need to promise that the total mass sums to at most one. And this is what makes it able to be interpreted as a probability.

Now, for some of you who might be more familiar with probabilistic programming stuff, you might be a little bit worried that I’m not doing some measure theory here. But generators are always going to be generating in countable domains. And so we actually don’t need to worry about measure theory here. 


def genFrames : G (List Frame) :=

      let ns ← genFrames

  ]
Okay, once we have this SPMF interpretation of generators, we can interpret a generator like genFrames as a distribution. And we can see that it produces empty lists with probability one half, and one-element lists with probability one fourth, et cetera. This is not a particularly good distribution, but now we can know that for sure. And importantly here, the probability of divergence is actually going to be zero.

run an SPMF?

Okay, there’s one more thing I want to talk about now that we’ve gotten the proof stuff out of the way, which is, how do you actually run one of these generators? Because an SPMF is actually not runnable. In Lean, it’s a classical object.

Carette et al., Finally Tagless, Partially Evaluated, JFP 2009

And so the trick is that you don’t actually represent generators as SPMFs. You represent generators using a tagless final style. So, actually, what generators are in Basalt is universally quantified values, quantified over some generator type.

So, the way this genFrames actually ends up being typed is: for all G, which are type constructors, assuming G satisfies a generator type class, then the value is of type G of List Frame. This allows us to interpret a generator at lots of different kinds of types, which satisfy the Gen type class.

Now that we have this tagless final embedding, we can interpret generators in all sorts of ways. So, for example, we can interpret them as SPMFs, or SPMFs that track cost. This way we can prove things about the number of choices that a generator needs to produce a given value.

We can run them both in IO for standard PBT and with a fuzzing back end for fuzzing.

And maybe we can do other things. I’d love if you have ideas for kinds of things that we might be able to interpret these generators as.

  instRandomChoice : RandomChoice G
  instCCPO         : ∀ α, CCPO (G α)

Here’s the Gen type class for you, just so you can see what it looks like. It has two main parts. The first is that generators have to be monads with random choice. This is classic QuickCheck stuff.

But the second part is, I think, what’s a little bit more unique about Basalt. Generators need to be CCPOs. This gives us Knaster–Tarski fixed points, and in some recent code that has been implemented in Lean, and that is now supported by the language, this allows us to write non-terminating definitions, but still prove things about those non-terminating definitions, because the definition is well formed as a Knaster–Tarski fixed point. If you don’t know what that means, don’t worry.

The last question I want to answer is, can generators in Lean be fast? Are people actually gonna want to run these things? It’s nice that you can prove things and run the same generator. But do you actually want to run them in Lean?
And it turns out the answer is yes. And it’s because I implemented some tricks from a paper by some collaborators and I.

So, the main reason one might not want to run these generators is that when you use combinators like frequency, you end up allocating quite a bit of memory. Because every time you evaluate this combinator, you actually have to allocate memory for this list here.

Richey and Cutler et al., Fail Faster, OOPSLA 2026

So, what I do in Basalt is this trick from a paper by Richey and Cutler, which I’m on, from OOPSLA just last week. And the idea is to replace these frequency combinators with elaborator macros. And so this frequency will actually elaborate to just an if chain. And then it’ll also elaborate to a proof that that if chain is the same as the original frequency.

And so, when running the generator, we get to use this if chain, which is really fast and doesn’t allocate. And when proving things about the generator, we get to use this kind of nicer frequency form.

And it turns out that implementing this makes our generators quite a bit faster. So in some examples, the generator gets over three times faster. And it turns out, actually, that the generator is also faster than Haskell QuickCheck, and also OCaml’s Base QuickCheck. So running these generators in Lean is actually faster than in many other programming languages in head-to-head comparisons.
