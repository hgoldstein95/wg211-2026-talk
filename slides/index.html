The other day, I went to my friendly neighborhood robot and asked for an implementation of Minecraft, written in Lean,

2.5 hours

And this took me about two and a half hours. [click] I mean, it took Claude two and a half hours. This was not some huge effort, and it did not take a tremendous amount of expertise from me. It took some, but this was basically all done for me. So the question for me was: then why do we need testing? Can’t we just prove all of these things correct?
But pulling back the curtain a little on what Claude built, I realized it hadn’t done exactly what I asked. Rather than implement the core rendering logic in Lean, which would have been hard to do efficiently because the game needs to talk to the GPU, it used a library, raylib, in C. In principle I’m not against this: it would not have been useful to go off and emit GPU code directly from Lean. So I was perfectly fine with it. But it left me wondering: how do I know that the proofs are correct relative to the semantics of raylib? [click] And this is where testing came in. I had Claude go back and build a model, in Lean, of what it thought raylib was going to do, and test that model against the real thing. [click] And then prove that the theorems it had shown were correct relative to that modeled semantics.
And I think this is where testing needs to stay. Even if we end up writing all of our code in proof systems like Lean, Rocq, F*, Verus, and so on, [click] we will ultimately need to test the relationships between the semantics of the component pieces of real software systems. The idea that all software will be written in one homogeneous language just doesn’t fit the way software engineering has developed over decades, and I don’t believe that’s going to change any time soon, for social reasons if not technical ones.
So let’s dig a little deeper into what these tests look like. We have our model, and we have raylib. [click] We’re going to generate a bunch of commands for both of them, sequences of commands, and ask: do they produce the same result? [click] And to produce all those sequences of commands, we need a program called a generator. That’s the PBT term for the random program that produces inputs to a system under test.

How do we make
generators good?

And what should "good" even mean?

The question I’m going to answer with the rest of this talk is: how can we make sure those generators are as good as possible, so that we can believe the relationship we’re claiming between our model and our implementation? [click] And a side question is: what does “good” even mean? That’s something I’m going to ask all of you about, because I really do need feedback here. I’m writing a paper, and there are things in the evaluation, and in the demonstration of what we can do, that could use some punching up.
I’m going to talk about two systems. The first is Palamedes, which was presented at PLDI this year. [click] The other is Basalt, a new foundational abstraction for PBT generators. It isn’t published yet, but we’re working on a paper for it as well.

Palamedes

Synthesizing Generators

So first, let’s talk about Palamedes.

So how are we going to get a generator for these frames? In our system, Palamedes, which we presented at PLDI, we showed a scheme for deductive synthesis that produces generators from a predicate. [click] So what we’re ultimately going to do is implement genFrames with this tactic, generator_search, which ensures that we produce a generator that is both sound and complete with respect to the predicate. 

∃ g : G α, g.support = P
So what is the tactic proving? An existential. [click] There exists a generator, [click] and its support is exactly the predicate: it samples exactly the values that satisfy P, which is sound and complete. And the way to prove an existential is to instantiate it. The witness the search builds is the generator. 

inductive ListF (α β : Type)
  | nilF
  | consF (head : α) (rest : β)

Here is that predicate for one layer. The search reads its logic off as a program, one connective at a time. [click] So take it apart: an or, over its two sides. [click] s_pick: a disjunction is a choice. [click] s_pure: an equation is a constant. [click] s_bind: an existential is a draw, and the and is the semicolon: draw n, and then go on with it. [click] s_between: a bound is a range. [click] s_pure again, and every piece is program. [click] Put it back together, the semicolon as a line break: a generator for one layer. Nothing changed places but the or. Every rule comes with its proof, so the generator samples exactly the predicate. The rules are real. The liberties: the search works on goals from the top down, not on loose pieces; s_bind takes the existential and its conjunction as one, and gives a bind, written here as a do block; s_pick gives pick, spelled oneOf here; s_between wants both bounds; the real layer goal wraps the check in guard; and the search applies every rule under convert. 

def framesOK (fs : List Frame) : Bool :=
  List.fold
    (fun
      | .nilF => true
      | .consF n ok => n ≤ 200000 && ok)
    fs
So that is a generator for one layer. Back in framesOK, what is left is the fold itself, which is where the recursion lives.
Tie it together. A fold turns a value into a boolean: a list goes in, true comes out. [click] So run it backwards. An unfold turns the boolean back into a value: start from true, and out comes a list the fold accepts. Which one is not determined, and that is exactly a generator. The search built one layer of this: if one step of the unfold undoes one layer of the fold, the unfold undoes the whole fold. A fudge on the slide: the real unfold starts from a seed, here a unit, not from true. 

theorem fold_unfold_inverse
    (alg  : ListF α β → β)
    (step : β → G (ListF α β)) :
    (∀ b, (step b).support =
      fun l => alg l = b) →
    (∀ b, (List.unfold step b).support =
      fun xs => List.fold alg xs = b)
That last sentence, as a theorem. alg is what the fold does with one layer; step is what the unfold does with one seed. [click] Suppose that, for every b, the step samples exactly the layers that alg sends to b: one layer, undone. [click] Then the unfold from b samples exactly the lists that fold to b: the whole fold, undone. The premise is what the search just discharged, piece by piece. This rule is what turns it into a generator for lists, and the recursion is proved once, here, for every predicate that is a fold. This is the paper’s S-List-Unfold′ in the deck’s spelling, not checked in Lean in this form; the rule the search applies, List.s_unfold, is more general. Read literally for framesOK, the seed is true at every step, as in the picture; the generator on the next slide has a unit there.

Palamedes lets us synthesize

What to take from Palamedes. It turns the predicate you already have into a generator. The generator is sound and complete by construction: it is found together with its proof. And recursion comes for free: a predicate that is a fold has a generator that is an unfold.

Basalt

Generators with proofs

What does a
generator mean?

Signpost, part one of three. Palamedes left us with a number we could measure and not state. So start with what a generator means. 

def QC.Gen α := Seed → α

def QC.support (g : QC.Gen α) : Set α :=
  {x | ∃ s, g s = x}
            

QC.support genFrames = {ns | framesOK ns}
We measured that 49.2%. Can we state it? The existing foundation is QuickChick (Paraskevopoulou et al., Foundational Property-Based Testing, ITP 2015): a generator is a function from seeds, and its meaning is the set of values it can produce. Palamedes started from this semantics too. [click] So this is everything it can say about genFrames: every valid list can come out. That is what Palamedes proved, and it is silent on half of them being empty. The last line is how that semantics would put it; it is not from QuickChick. 

def SPMF (α : Type) : Type :=
  {μ : α → ℝ≥0∞ // (∑' a, μ a) ≤ 1}
So a generator should mean a distribution, not a set. This is Basalt’s. [click] A mass for every value: for genFrames, by length, a half for the empty list, a quarter for one frame, and so on. That half is the 49.2%, and now it is something we can write down. [click] And the masses may sum to less than one: what is missing is the chance of no answer at all. For genFrames that is zero, which is a theorem coming up. The bars follow from the generator choosing evenly between two branches; they are not themselves a theorem in talk-code/Frames.lean.

How do you run
a distribution?

Signpost, part two. A distribution is the right meaning, but it is a mathematical object, and a test has to run something. This part builds to the engagement point on the readings slide, and then to what the embedding costs to write and to run. 

def genFrames [Gen G] : G (List Nat) :=
  oneOf! [
    fun _ => pure [],
    fun _ => do
      let n ← genElapsed
      let ns ← genFrames
      return n :: ns
  ]
partial_fixpoint
A distribution is a mathematical object, and a test has to run something. Which one is the generator? Both. This is genFrames as you would write it in QuickCheck. [click] It is polymorphic in its interpretation: G is any monad with random choice. [click] And its recursion is a least fixed point. genElapsed makes one frame time; hold that thought, we open it up in a few slides. Checked, as written (talk-code/Frames.lean). 

class Gen (G : Type → Type) where
  instMonad        : Monad G
  instRandomChoice : RandomChoice G
  instCCPO         : ∀ α, CCPO (G α)
  instMonoBind     : MonoBind G
The tagless-final embedding: this is everything an interpretation has to provide. [click] One operation, choose, is the only source of randomness; every combinator is built on it. [click] And a chain-complete partial order with a monotone bind, which is what partial_fixpoint needs. As in Basalt/Gen.lean, less an Inhabited field.

The payoff of the embedding: the same term at different types. [click] At IO it runs. [click] At SPMF it is the distribution from the picture, which is what the proofs are about: the code you prove things about is the code you run. [click] SPMF.Cost also counts random choices, and FuzzGen reads its choices from a byte buffer, so a coverage-guided fuzzer drives generation. Also: Plausible.Gen, and a statistics interpretation behind #genstats.

One thing the embedding buys before any proof: you write the generator the way you would anyway. Its recursion is a least fixed point, so nothing has to decrease. [click] Where generators are ordinary total functions, this is what you write instead. And the fuel ends up in every specification: the support becomes the lists of length at most fuel. That is what happened in the game’s own tests: the run generators are listOfMaxLength n, and their proved spec says length ≤ n. The fuel listing is written for the slide; not from QuickChick.

frequencyWith

      else default)
  _                           -- a proof they are equal
One more thing the embedding has to get right before any proof: speed. Some of you have been wondering about the bang. A choice between branches is a list of closures, built and walked on every draw. [click] So frequency! is a macro, and it elaborates to three things: the plain frequency, which is what every proof sees; the code that runs, one draw and a chain of tests, with the running totals 2, 7 and 10 added up while the macro runs; and a proof that the two are equal, which the kernel checks. frequencyWith just returns the second. oneOf! is the same with equality tests. This is what #print shows for the definition, with notation off, less the fun _ => thunks around each branch (Basalt/Combinators.lean).
And it matters. Four benchmarks: search trees, heaps, sorted lists, and a bare natural number. With the plain combinators, Basalt is slower than QuickCheck on every one. With the macros it is 1.8 to 3 times faster than itself, and ahead of QuickCheck on every one, by 1.2 to 1.7 times. Base_quickcheck is behind QuickCheck throughout, so it is not drawn. And every proof still sees the plain combinator. Numbers: geometric mean of 20 rounds on an Apple M5 Max, values per second of CPU time; the first three generate a value, serialize it to JSON and write it, and the last only generates (basalt-raw-speed, results/2026-09-26-ablation). The other ablation there, SplitMix against Lean’s own random numbers, is worth about as much again.

What do proofs
buy you?

Signpost, part three. We can write it and run it. Now the reason for all of it. Everything from here builds to the open slot on the last slide. 

theorem genFrames.sound_complete :
    IsSoundAndComplete genFrames framesOK

theorem genFrames.terminates :
    IsAlmostSurelyTerminating genFrames

theorem genFrames.expect_length :
    SPMF.expect genFrames (·.length) ≤ 1
Now the proofs. For genFrames, with no fuel anywhere: it makes exactly the valid lists, which is all the set semantics could say. [click] It terminates with probability 1: the empty slot in the picture. [click] And a run is at most one frame long on average: the statistic from the end of Palamedes, as a theorem. All three are checked. There the spec is the Prop FramesOK, and the length is cast to ℝ≥0∞. From here on, every slide is something a proof buys, building to the last engagement point.

What to take from Basalt, one answer per question. A generator means a distribution, so “how often” is something you can say. One term is both the code you run and the object you prove things about, with no fuel, and fast.
